# PCI Colombo — Cloud Firestore Data Model (Draft v1)

**Project:** PCI Colombo Smart Pest Control Service Management System  
**Team:** LNBTI ICT2410 — Group F  
**Storage:** Cloud Firestore (Firebase project `PCI-Colombo-Team-F`)  
**Clients:** React web (Main Admin, Sub Admin, Customer); React Native/Expo (Employee)  
**Backend:** One Node.js/Express REST API using Firebase Admin SDK  
**Status:** **Proposed design — review and approve before writing seed scripts or production code.**

## 1. How to read this document

- A **collection** contains many **documents**. A document has an ID and typed fields. This is not a relational SQL schema.
- `string`, `boolean`, `number`, `timestamp`, `array<string>`, and `map` describe intended Firestore types. Monetary values use **integer minor units** (`amountCents`, LKR cents) consistently; quantities use numeric values plus `unit`.
- `?` means optional. `ref:collection` means **a string document ID** pointing to another collection, NOT a database-enforced foreign key.
- Every business document gets `createdAt: timestamp` and `updatedAt: timestamp` unless explicitly stated otherwise; records with human actions also get appropriate actor ID fields.
- Document IDs should be generated by Firestore (`auto-ID`) except `users/{firebaseAuthUid}`. Prefer immutable IDs, not names or email addresses.
- In most cases use **top-level collections** to simplify querying and cross-module workflows. Use nested maps for small fixed groups of related fields. Do not embed indefinitely growing data arrays in one document.
- **Authentication:** Firebase Authentication owns credentials and password handling. Do **not** save passwords, password hashes, tokens, or secrets in Firestore.
- **Authorization:** Only the Express backend, after verifying Firebase ID tokens, reads/writes business documents through the Admin SDK. Deny-all direct Firestore client rules remain in place. All access checks and business validation live in backend services.
- **Development data:** Only fictional information; no real client records or actual chemical compliance claims.

## 2. Collection catalog (all four modules)

### 2.1 Accounts and access — Shared; lead: Yasasmi

#### `users/{uid}`
**Purpose:** Application profile linked to Firebase Authentication. **Document ID:** Firebase Auth UID.

| Field | Type | Notes |
|---|---|---|
| `displayName` | string | Required |
| `email` | string | Email from verified Auth account; not used as document ID |
| `phone` | string? | Optional |
| `roleIds` | array<string> | Initial role values: `main_admin`, `sub_admin`, `customer`, `employee`; assigned only by authorized backend |
| `status` | string | `active`, `suspended`, `disabled` |
| `profileType` | string | `customer`, `employee`, or `staff` as applicable |
| `createdAt`, `updatedAt` | timestamp | Audit metadata |

**Rules:** Users cannot grant themselves roles. Backend verifies token and reloads current status/permissions on protected requests. Choose a consistent server-side policy for multi-role accounts.

#### `roles/{roleId}`
`name: string`, `description: string`, `active: boolean`. Recommended fixed IDs: `main_admin`, `sub_admin`, `customer`, `employee`.

#### `permissions/{permissionId}`
`name: string`, `description: string`, `module: string`. Example `inventory.manage`. **Do not let a client modify permissions.**

#### `rolePermissions/{roleId}`
`permissionIds: array<string>`, `updatedByUid: ref:users`, `updatedAt: timestamp`. One document per role to avoid a many-to-many join collection. Exact permissions require a reviewed access matrix.

### 2.2 Main Admin — Yasasmi

#### `employees/{employeeId}`
`userUid: ref:users`, `employeeCode: string`, `fullName: string`, `contactNumber: string?`, `specializations: array<string>`, `hireDate: timestamp?`, `employmentStatus: string` (`active`, `inactive`), `createdAt`, `updatedAt`. `userUid` must identify an appropriate authenticated employee account.

#### `leaveRequests/{leaveId}`
`employeeId: ref:employees`, `leaveType: string` (`half_day`, `one_day`, `multiple_day`), `startDate: timestamp`, `endDate: timestamp`, `halfDaySession: string?` (`morning`, `afternoon`), `reason: string`, `status: string` (`pending`, `approved`, `rejected`, `cancelled`), `reviewedByUid: ref:users?`, `reviewedAt: timestamp?`, `reviewNote: string?`, `createdAt`, `updatedAt`.

**Rules:** End date must not precede start date; half-day requests require a session; only authorized Main Admin approves/rejects; approved leave is checked during assignment. Resolve reassignment when leave overlaps visits.

#### `serviceCategories/{categoryId}`
`name: string`, `description: string?`, `active: boolean`, `createdAt`, `updatedAt`. **Service categories** (e.g. inspection/treatment) are distinct from **pest categories** below.

#### `pestCategories/{pestCategoryId}`
`name: string`, `description: string?`, `active: boolean`. Initial proposed names: rats, cockroaches, subterranean termites, mosquitoes, bed bugs. IDs should be stable slugs.

#### `inventoryItems/{itemId}`
`name: string`, `itemType: string` (`chemical`, `equipment`, `other_consumable`), `sku: string`, `unit: string`, `quantityOnHand: number`, `quantityReserved: number`, `reorderLevel: number`, `pestCategoryIds: array<string>` (refs to `pestCategories`), `batchNumber: string?`, `expiresAt: timestamp?`, `approvalStatus: string?` (`pending_review`, `verified`, `rejected`, `expired`), `isActive: boolean`, `createdAt`, `updatedAt`.

**Rules:** Available quantity = on-hand minus reserved; never negative. Chemicals must pass verified approval, expiry and safety checks before allocation. For multiple chemical batches/expiries, migrate to separate `inventoryBatches` documents before implementing batch-level allocations. Equipment should ultimately be tracked by unit or checked-out quantity, not 'consumed' as chemicals are.

#### `stockMovements/{movementId}`
`itemId: ref:inventoryItems`, `movementType: string` (`receipt`, `adjustment`, `consumption`, `return`, `write_off`), `quantityDelta: number`, `unit: string`, `reason: string`, `visitId: ref:serviceVisits?`, `recordedByUid: ref:users`, `recordedAt: timestamp`, `createdAt`. Use an immutable event record rather than deleting stock history.

#### `complianceDocuments/{documentId}`
`title: string`, `documentType: string` (`company_license`, `chemical_registration`, `safety_data_sheet`, `certificate`, `other`), `relatedItemId: ref:inventoryItems?`, `filePath: string?` (Firebase Storage path, not secret download token), `issuer: string?`, `referenceNumber: string?`, `issuedAt: timestamp?`, `expiresAt: timestamp?`, `verificationStatus: string` (`pending`, `verified`, `rejected`, `expired`), `verifiedByUid: ref:users?`, `verifiedAt: timestamp?`, `visibleToCustomer: boolean`, `createdAt`, `updatedAt`.

**Rules:** Only verified, relevant, non-expired documents may be shown as verified. Store the actual approved files in secured Storage if/when Storage is configured; do not fabricate approvals.

### 2.3 Customer — Dulni

#### `customers/{customerId}`
`userUid: ref:users`, `customerType: string` (`individual`, `organization`), `displayName: string`, `organizationName: string?`, `contactPerson: string?`, `phone: string?`, `status: string` (`active`, `inactive`), `createdAt`, `updatedAt`.

#### `serviceLocations/{locationId}`
`customerId: ref:customers`, `name: string`, `addressLine1: string`, `addressLine2: string?`, `city: string`, `contactPerson: string`, `contactNumber: string`, `premisesType: string?`, `accessInstructions: string?`, `status: string` (`active`, `archived`), `createdAt`, `updatedAt`.

**Rules:** Customer owns location; do not hard-delete a location with historical requests/jobs; archive it.

#### `serviceRequests/{requestId}`
`customerId: ref:customers`, `locationId: ref:serviceLocations`, `serviceCategoryId: ref:serviceCategories`, `pestCategoryIds: array<string>`, `description: string`, `preferredVisitAt: timestamp?`, `priority: string` (`normal`, `urgent`), `status: string` (`submitted`, `under_review`, `inspection_scheduled`, `quoted`, `closed`, `cancelled`), `createdAt`, `updatedAt`.

**Rules:** The location must belong to the customer. Only permitted status transitions are allowed. Sub Admin controls operational review state.

#### `siteSafetyAssessments/{assessmentId}`
`requestId: ref:serviceRequests`, `locationId: ref:serviceLocations`, `reportedIndicators: map` (`childrenPresent`, `olderAdultsPresent`, `petsPresent`, `foodAreasPresent`, `otherConcerns`), `customerNotes: string?`, `reviewStatus: string` (`pending`, `reviewed`, `requires_followup`), `reviewedByUid: ref:users?`, `reviewedAt: timestamp?`, `createdAt`, `updatedAt`.

#### `safetyNotices/{noticeId}`
`visitId: ref:serviceVisits`, `customerId: ref:customers`, `noticeVersion: number`, `approvedContent: string`, `issuedByUid: ref:users`, `issuedAt: timestamp`, `acknowledgedAt: timestamp?`, `acknowledgedByUid: ref:users?`, `status: string` (`draft`, `issued`, `acknowledged`, `superseded`), `createdAt`, `updatedAt`.

#### `treatmentProposals/{proposalId}`
`visitId: ref:serviceVisits`, `proposedItemIds: array<string>` (refs to approved `inventoryItems` where relevant), `description: string`, `precautionSummary: string`, `version: number`, `reviewedByUid: ref:users?`, `reviewedAt: timestamp?`, `status: string` (`draft`, `approved`, `superseded`), `createdAt`, `updatedAt`.

**Rules:** Proposals reflect authorized professional decisions; the software must not prescribe chemical use or invent safety guidance. Changing material treatment details creates a new version and requires renewed customer consent as appropriate.

#### `treatmentConsents/{consentId}`
`proposalId: ref:treatmentProposals`, `proposalVersion: number`, `visitId: ref:serviceVisits`, `customerId: ref:customers`, `decision: string` (`accepted`, `declined`), `decidedByUid: ref:users`, `decidedAt: timestamp`, `noticeId: ref:safetyNotices?`, `createdAt`.

**Rules:** Quotation acceptance is separate from treatment consent. Preserve the proposal version and decision as an auditable record. No self-assignment of customer ownership.

#### `feedback/{feedbackId}`
`customerId: ref:customers`, `jobId: ref:serviceJobs`, `rating: number`, `comment: string?`, `createdAt`, `updatedAt`. Validate rating range (proposed: 1–5) and ensure customer owns the referenced job.

#### `faqs/{faqId}`
`question: string`, `answer: string`, `category: string`, `active: boolean`, `updatedByUid: ref:users?`, `createdAt`, `updatedAt`.

#### `chatSessions/{sessionId}`
`customerId: ref:customers?`, `startedAt: timestamp`, `endedAt: timestamp?`, `status: string` (`active`, `closed`). Optional: do not store conversations unless needed for the approved scope.

#### `chatMessages/{messageId}`
`sessionId: ref:chatSessions`, `sender: string` (`customer`, `bot`), `messageText: string`, `faqId: ref:faqs?`, `createdAt`. Minimize stored personal information and set retention expectations.

### 2.4 Sub Admin — Sunera

#### `siteInspections/{inspectionId}`
`requestId: ref:serviceRequests`, `assignedEmployeeId: ref:employees?`, `scheduledAt: timestamp?`, `performedAt: timestamp?`, `findings: string?`, `areaSize: number?`, `areaUnit: string?`, `severity: string?`, `status: string` (`planned`, `completed`, `cancelled`), `createdAt`, `updatedAt`.

#### `quotations/{quotationId}`
`requestId: ref:serviceRequests`, `inspectionId: ref:siteInspections?`, `version: number`, `status: string` (`draft`, `sent`, `revision_requested`, `accepted`, `rejected`, `expired`, `superseded`), `currency: string` (`LKR`), `subtotalCents: number`, `discountCents: number`, `taxCents: number`, `totalCents: number`, `validUntil: timestamp?`, `preparedByUid: ref:users`, `sentAt: timestamp?`, `respondedAt: timestamp?`, `createdAt`, `updatedAt`.

**Rules:** Preserve earlier versions; only one accepted version should create a given job. Financial totals are calculated and verified on the server. Customer response permitted only for their own request.

#### `quotationItems/{itemId}`
`quotationId: ref:quotations`, `description: string`, `quantity: number`, `unit: string`, `unitPriceCents: number`, `lineTotalCents: number`, `costType: string` (`labor`, `materials`, `inspection`, `other`), `createdAt`. A separate collection supports itemized revisions and querying.

#### `serviceJobs/{jobId}`
`quotationId: ref:quotations`, `requestId: ref:serviceRequests`, `customerId: ref:customers`, `locationId: ref:serviceLocations`, `status: string` (`created`, `scheduled`, `in_progress`, `completed`, `cancelled`), `createdByUid: ref:users`, `createdAt`, `updatedAt`.

**Rules:** Create only after accepted quotation; verify customer/location consistency. A job can have many visits.

#### `serviceVisits/{visitId}`
`jobId: ref:serviceJobs`, `scheduledStart: timestamp`, `scheduledEnd: timestamp`, `status: string` (`scheduled`, `assigned`, `confirmed`, `in_progress`, `completed`, `cancelled`, `on_hold`), `safetyStatus: string` (`pending_review`, `cleared`, `on_hold`), `visitNumber: number`, `createdAt`, `updatedAt`.

**Rules:** End after start; assignments cannot conflict with approved leave or overlapping active assignments; unresolved safety concerns can place visit on hold.

#### `employeeAssignments/{assignmentId}`
`visitId: ref:serviceVisits`, `employeeId: ref:employees`, `status: string` (`assigned`, `confirmed`, `declined`, `cancelled`, `completed`), `assignedByUid: ref:users`, `assignedAt: timestamp`, `respondedAt: timestamp?`, `createdAt`, `updatedAt`.

#### `resourceAllocations/{allocationId}`
`visitId: ref:serviceVisits`, `inventoryItemId: ref:inventoryItems`, `quantityReserved: number`, `unit: string`, `status: string` (`reserved`, `issued`, `released`, `consumed`, `returned`), `allocatedByUid: ref:users`, `createdAt`, `updatedAt`.

**Rules:** Stock reservation uses a transaction to check available quantity and adjust reserved balance atomically. Distinguish equipment return and chemical consumption.

#### `recurringAgreements/{agreementId}`
`customerId: ref:customers`, `locationId: ref:serviceLocations`, `sourceJobId: ref:serviceJobs?`, `frequency: string` (`monthly`, `quarterly`, `custom`), `intervalDays: number?`, `startDate: timestamp`, `endDate: timestamp?`, `nextDueAt: timestamp?`, `status: string` (`active`, `paused`, `ended`), `createdAt`, `updatedAt`.

#### `invoices/{invoiceId}`
`jobId: ref:serviceJobs`, `customerId: ref:customers`, `invoiceNumber: string`, `currency: string` (`LKR`), `totalCents: number`, `paidCents: number`, `balanceCents: number`, `status: string` (`draft`, `issued`, `partially_paid`, `paid`, `void`), `issuedAt: timestamp?`, `dueAt: timestamp?`, `createdAt`, `updatedAt`.

**Rules:** Do not delete financial history; void/correct with audit information. Calculate balances from verified payment records, not customer-entered values.

#### `payments/{paymentId}`
`invoiceId: ref:invoices`, `customerId: ref:customers`, `amountCents: number`, `currency: string` (`LKR`), `method: string` (`online`, `cash`, `cheque`), `status: string` (`pending`, `submitted`, `verified`, `rejected`, `failed`, `refunded`), `gatewayReference: string?`, `offlineReference: string?`, `verifiedByUid: ref:users?`, `verifiedAt: timestamp?`, `createdAt`, `updatedAt`.

**Rules:** Never store card details. Only verified gateway callbacks or authorized offline review may change payment to `verified`; update invoice totals atomically and idempotently.

## 3. Key cross-module relationships

| Origin | Referenced record | Meaning / validation |
|---|---|---|
| `users/{uid}` | `employees.userUid` or `customers.userUid` | A Firebase account has a linked profile; one-to-one policy enforced by backend |
| `serviceLocations.customerId` | `customers` | Customer owns location |
| `serviceRequests.locationId` | `serviceLocations` | Request belongs to an authorized customer's active location |
| `quotations.requestId` | `serviceRequests` | Quotation is for a specific request |
| `serviceJobs.quotationId` | `quotations` | Job may only originate from an accepted quotation |
| `serviceVisits.jobId` | `serviceJobs` | A job has multiple visits |
| `employeeAssignments.visitId` | `serviceVisits` | Employee is assigned to an individual visit |
| `resourceAllocations.inventoryItemId` | `inventoryItems` | Visit reserves stock/equipment |
| `chemicalUsage.allocationId` | `resourceAllocations` | Actual use is reconciled with reserved resources |
| `treatmentConsents.proposalId` | `treatmentProposals` | Consent refers to an exact reviewed proposal version |
| `invoices.jobId` | `serviceJobs` | Invoice corresponds to a job |
| `payments.invoiceId` | `invoices` | Verified payments affect balance |
| `leaveRequests.employeeId` | `employees` | Approved leave constrains scheduling |

## 4. Essential application rules and access matrix

| Action | Main Admin | Sub Admin | Customer | Employee |
|---|---|---|---|---|
| Manage users, roles, categories, inventory, compliance | Yes | View relevant stock/compliance | View verified applicable docs | View assigned equipment/safety info |
| Approve leave | Yes | View availability | No | Submit own request |
| Requests, inspections, quotations and jobs | Reports/oversight as authorized | Manage | Own requests and quotation decisions | Assigned inspections only |
| Visit scheduling and resource allocation | Inventory support | Manage | View own visits | View/respond to own assignments |
| Reports, usage and checklists | Compliance oversight | Review reports | View own permitted reports | Submit for own assigned visits |
| Invoices and payments | Reports/oversight as authorized | Issue/verify | Own invoices and payment submissions | No |
| Safety review and consent | Manage verified compliance info | Approve operational safety notices/holds | Provide info and consent for own visits | Complete safety checks and report concerns |

This matrix must be implemented and tested **server side**. Validate all IDs, ownership, allowable status transitions and numeric fields; never trust the role claimed by a request body.

## 5. Data integrity and workflow checks

1. **Authentication:** Client sends Firebase ID token over HTTPS; Express verifies token with Admin SDK and loads current user/role. Disabled users are blocked.
2. **Service workflow:** `request → inspection (where required) → quotation → accepted quotation → job → visit → employee assignment → report → invoice → payment`. Avoid skipping acceptance and safety gates.
3. **Concurrent scheduling:** Check overlapping visits and approved leave when assigning/reassigning employees; implement concurrency-safe reservations/locks or equivalent server-side consistency mechanism before production use.
4. **Inventory:** Reserve stock, issue items, record actual consumption/returns and update balances consistently via Firestore transactions. Reconcile stock ledger with balances.
5. **Safety:** Record verified compliance documents, review site assessments, keep treatment proposal versions and separate consent decisions; unresolved flags put visits on hold pending authorized review.
6. **Payments:** Verify provider callbacks server-to-server, protect against replay using unique references/idempotency, and recalculate invoice balances atomically.
7. **Deletion:** Prefer archival/inactivation for historical locations, accounts, financial records, inventory transactions and safety audit records. Set retention rules before handling real data.
8. **Indexes:** Add composite Firestore indexes based on actual query patterns, such as requests by customer and date, visits by employee and start time, and stock by status. Do not guess index definitions before API queries exist.
9. **Data protection:** Keep Firestore direct-client rules deny-all for this backend-only architecture; Admin SDK bypasses rules, so backend permissions are mandatory. Restrict developer Firebase project permissions and keep credentials out of Git.
